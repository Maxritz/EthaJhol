# Quantization support

`src/quant.c` holds the only quant table in the tree (`g_info[]`), and `src/gguf.c` derives
block geometry from it. Before this was unified the loader kept a second hand-written copy that
had already drifted (Q1_0 was listed as 32 weights per block instead of 128) and could not
parse ternary types at all, so files were rejected as malformed before the probe ever saw them.

## Ternary decoding (bit-exact with ggml)

The ternary layouts interleave bit-planes, so a decoder that walks the bytes linearly produces
the right multiset in the wrong positions — a bug that a naive sum comparison cannot see. The
implementations in `src/quant.c` (`deq_tq1_0`, `deq_tq2_0`, `deq_q1_0`, `deq_q2_0`) follow
`ggml-quants.c` exactly, including element order:

* **TQ2_0** — 64 packed bytes per 256 weights. For each 32-byte group, plane `l` occupies
  elements `group*4 + l*32 … +31`, extracted as `(qs[m] >> (2*l)) & 3` with codes mapped to
  `{-1,0,+1,+2}`. Scale is fp16 and comes last.
* **TQ1_0** — 48 bytes hold 5 values each (radix-3: `q*3^n`, then `((q*3)>>8) - 1`), 4 further
  bytes hold one value per plane, and the fp16 scale is last.
* **Q1_0 / Q2_0** — scale first, then 16 packed bytes (1 or 2 bits per weight).

`tests/test_quant.c` pins this with golden vectors generated by an independent Python port of
the upstream decoders, checking the first eight values *and* the position-weighted sum.

## Kernel strategy

All quantized matvecs are memory bound: a 4096x4096 Q4_0 matvec streams 9 MiB to do 33 M MACs.
The kernel therefore optimises bytes moved and instruction dependency, not FLOPs:

* weights stay packed; no dequantized matrix is ever materialized;
* one packed byte feeds every plane it encodes (the TQ2_0 kernel loads each byte once and runs
  four accumulator chains from it — this alone took TQ2_0 from 7.9 ms to 3.1 ms per matvec);
* two-row interleaving for Q4_0/Q4_K gives the scheduler an independent chain while the nibbles
  of the first row unpack;
* `__builtin_prefetch` one block ahead on the weight stream;
* row-parallel across threads with per-row arithmetic order preserved, so results are
  bit-identical to the single-threaded reference (asserted by `test_matmul_parity`).

## Not implemented

`Q8_1`, `IQ1_S`, `IQ1_M`, `IQ2_XXS`, `IQ2_XS`, `IQ2_S`, `IQ3_XXS`, `IQ3_S`, `IQ4_XS`, `MXFP4`,
`NVFP4` and `F64` are *known* to the table (so `inspect`/`probe` can name them) but have no
kernel. `vg_model_probe` rejects such a model up front and names the exact tensor and type:

```
model not supported: tensor 'blk.0.attn_q.weight' uses IQ2_XXS, which has no CPU dequantizer
```

## Adding a type

1. Add the enum value and table row in `include/vg/quant.h` / `src/quant.c`.
2. Add a `deq_*` function and register it in `block_fn()`.
3. Optionally add a fused kernel in `src/cpu_ops.c` and register it in `pick_rows()`; otherwise
   the generic per-row path is used (correct, one row buffer, slower).
4. Add golden bytes to `tests/test_quant.c` and a `test_matmul_parity` call for the type.
5. Add a GPU shader only if `vg_vk_supports_type()` should report it — never advertise a type
   the GPU cannot execute.
